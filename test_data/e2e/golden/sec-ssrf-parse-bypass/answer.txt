The fetcher validated the URL hostname only once, before the first request, and then followed up to five redirects without re-checking: the allowlist decision came from `Fetcher.fetch()` in `server/app.py` using `urlsplit(url).hostname` on the caller's URL only, so `http://api.internal/redirect?to=http://169.254.169.254/` pivoted the fetch onto the blocked link-local metadata host and returned its body. The root cause is a check-then-redirect order: the allowlist was enforced on the parsed initial URL instead of on every connection actually opened (the same one-shot parse also lets a `user@api.internal@169.254.169.254` authority mislead a naive parser).

The fix moves the scheme check, a userinfo sanity check and `host_is_allowed()` inside the redirect loop so every hop, including each `Location` target, is validated before the connection is made, and rejects authorities that still contain an `@`. Redirects onto `169.254.169.254` and onto `.admin` names are refused with 403, the userinfo spelling is refused, and legitimate `api.internal` / `metadata.internal` fetches keep working. `python3 tests/integration_test.py` passes all 8 checks; the full write-up is in `report/fix.md`.
